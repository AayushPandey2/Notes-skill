# Multi-branch topic collections

Load whenever the requested topic naturally splits into multiple sub-branches/subtopics (whereas a focused concept without distinct sub-branches uses a single 3-file bundle). Use [adaptive planning](adaptive-engine.md) to identify concepts, prerequisites, and each subtopic's main note. Let the topic's real sub-branches determine chapter count; do not pad or split chapters to meet a quota. Keep an existing collection's layout when revising it.

Plan one `00 - Map of Contents.md` and numbered subtopic notes inside `<Configured Target>/<Topic>/`, emitting companion files per subtopic according to `artifact_policy` in [master-registry.yaml](../../dispatch/master-registry.yaml) (default 3-file bundle for `M1`/`M2` unless `explicit_single_file` or `existing_layout_preservation` overrides it) plus `<Topic>/assets/`. The map lists the learning path and links to actual subtopics. Before writing, check the vault for overlapping notes, user naming conventions, existing IDs, and backlinks. Do not silently replace user text or create additional category folders outside `<Topic>/`.

Author the final Markdown directly. Each chapter follows [teaching_core.md](../../../core/teaching_core.md) and [authoring_rules.md](../../../core/authoring_rules.md): open with separated metadata (`Difficulty`, `Prerequisites`, `Learning objectives`) and a compact **clickable Obsidian Table of Contents** (`- [[#1. Heading|Short Label]]`), write single-idea paragraphs anchored by concrete examples/tables before abstract terms, define essential notation locally before first use (reserving any Notation Reference for the end), and keep a single main explanatory home per concept. Bridge essential prerequisites locally (using [teaching guidance](../../../core/teaching_core.md) and [math guidance](../../../core/math_gates.md)), place complementary visuals at conceptual inflection points via [representations.md](representations.md) (respecting source-only limits), and close each chapter with a concise mental model and reciprocal links to any generated companions. Keep the user's source limits even when an external lookup would help.

New comprehensive M1 notes use exactly the five YAML keys `id`, `aliases`, `topic`, `tags`, `nexttopics` as described in [properties policy](../../properties/properties-policy.md). Existing notes keep user-managed properties and layout. Before saving, review the actual chapters for concept coverage, claims and citations, formula conditions, assessments, YAML, links, embeds, and accidental changes to existing content. Save the intended files with native tools, inspect what was saved, and report partial or unverified work honestly. No atomic collection transaction, checkpoint recovery, automatic hash binding, or automated educational acceptance is provided.
