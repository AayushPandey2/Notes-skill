# Multi-branch topic collections

Load whenever the requested topic naturally splits into multiple sub-branches/subtopics (whereas a focused concept uses a single-unit layout). Use [adaptive planning](adaptive-engine.md) to identify concepts, prerequisites, each chapter's main note, and chapter organization—letting the topic's real sub-branches determine chapter count without padding or splitting to meet a quota, and keeping existing collection layouts when revising.

Plan `00 - Map of Contents.md` and numbered subtopic notes inside `<Configured Target>/<Topic>/` strictly according to the resolved `artifact_plan` manifest ([adaptive-engine.md](adaptive-engine.md), driven by `artifact_policy` in [master-registry.yaml](../../dispatch/master-registry.yaml), explicit user requests, `source_permissions`, and existing vault layout), emitting only artifacts included in that manifest plus `<Topic>/assets/` when required assets exist. Before writing, check the vault for overlapping notes, user naming conventions, existing IDs, and backlinks. Do not silently replace user text or create additional category folders outside `<Topic>/`.

Author the final Markdown directly. Each chapter follows [teaching_core.md](../../../core/teaching_core.md), [theory_quality_contract.md](../../../core/theory_quality_contract.md), [math_gates.md](../../../core/math_gates.md), and [authoring_rules.md](../../../core/authoring_rules.md), keeping one main explanatory home per concept across the collection, placing complementary visuals via [representations.md](representations.md) within source limits, and closing with reciprocal links to any generated companions. Keep the user's source limits even when an external lookup would help.

Apply the collection profile in the [properties policy](../../properties/properties-policy.md). Follow the [authoring pipeline](../../../core/runtime_pipeline.md) for review, publication and partial-write reporting.
