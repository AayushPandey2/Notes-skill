# Companion experimental lab

For each newly generated content note, create or update exactly one sibling `<note stem> - Experimental Lab.md`. Exclude MOCs, labs, assets, and internal workflow documents; do not create labs retroactively across a vault. Link parent and lab reciprocally. Use the active metadata profile without adding keys, and preserve the parent's notation and source limits.

Choose **one** template from the practical learning objective, not a keyword. Use [Machine Learning](../../templates/labs/machine-learning.md) for data, fitting, validation, and inference; [Deep Learning](../../templates/labs/deep-learning.md) for tensors, architectures, gradients, and training dynamics; [Mathematics](../../templates/labs/mathematics.md) for proof, derivation, and counterexample; [Physics](../../templates/labs/physics.md) for physical models, measurements, and uncertainty; [Chemistry](../../templates/labs/chemistry.md) for chemical systems, reactions, and evidence; or [General](../../templates/labs/general.md) for another investigation. For an interdisciplinary objective, select the primary structure and incorporate relevant material inside it.

Use the selected template's headings and order, including its track headings. Begin with subject/topic, level, prerequisites, practical objective, investigation question, outcomes, materials or tools, expected deliverable, and constraints. Include languages and libraries for computational work; apparatus or substances for physical work. Adapt the shared progression: **Understand → Model or derive → Construct or investigate → Observe → Explain → Compare → Diagnose → Verify → Apply**.

## Code, Math & Explanation Standards

- **Complete code before breakdown:** Within an implementation track, show the full relevant program in a Markdown fence before its detailed breakdown; within a staged professional workflow, teach each stage individually and then assemble the integrated program in the designated assembly step. Keep names, inputs, fixtures, and parameter choices consistent throughout.
- **Brief visible summaries + collapsed walkthroughs:** Keep the main reading path concise. After each important code block, give a short visible explanation of purpose, output interpretation, and connection to the next operation, then place detailed syntax, variables, types, inputs, internal execution, mathematical correspondence, outputs, shapes, mistakes, and alternatives inside a collapsed Obsidian callout (`> [!example]- Step-by-step: how this operation works`), quoting every line including blank lines (`>`). Do not repeat an enormous generic checklist beneath trivial lines.
- **Mathematical-to-code mapping & formula folds:** Give every displayed `$$...$$` equation its own collapsed `> [!note]- 📐 Understand this formula` walkthrough per [math_gates.md](../../../shared/math_gates.md) without recursive nesting or raw LaTeX outside math delimiters. Expand math-to-code mappings step by step (data stored, iteration/operation, type conversion, calculation, small concrete trace, nonempty/precision limits) rather than one-line claims.
- **No thin substitute explanations:** Cross-references ("See Visual 1", "Matches Section 3.7") or one-line summaries ("`cargo new ...`", "This expression implements the mean") may supplement local reasoning, never replace it. For internal mechanisms, trace actual data flow, transformations, and intermediate states.
- **Rust & optional library tracks:** Explain Rust setup commands, file paths, compilation vs execution, slices/borrowing/ownership, bounds, and concrete small inputs in beginner-accessible collapsed walkthroughs. Decide optional Rust-library track applicability before drafting: if a documented crate genuinely helps and APIs are verified, include the complete track; if no library is warranted, **omit the optional Rust-library track** and briefly explain the choice in the implementation-selection discussion. Never generate hollow grouped placeholder ranges (such as `6.2–6.6 Limitation Note`).
- **Honest verification & execution status:** Use one clear execution-status statement per implementation (e.g., `Status: static review (not executed)` when unexecuted) without cluttering every heading. For every verification check, state: property checked, concrete inputs, independently expected results, comparison/tolerance, what it establishes, what it does not establish, and whether it was executed. Never invent measurements, code runs, or crate APIs.

Plan visuals section by section using [representations.md](representations.md) and **Orient → Show → Explain → Work through → Connect**. Native Mermaid explains flow; inspected local raster assets explain geometry, appearance, apparatus, structures, architecture, or graphs; tables show exact values. A general reference figure is not experimental evidence. Review the saved note and assets with [verification-checklist.md](../validation/verification-checklist.md).
